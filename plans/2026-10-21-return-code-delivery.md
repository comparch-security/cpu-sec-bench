## Summary

**The convention (shared values + reserved bands; gate-confirmed R1, 2026-10-22).** 0 = attack succeeded. **1** = attack not demonstrated — the single shared verdict constant. **2–14** = the case-local verdict space: any other failure value a case delivers is local to that case and must be declared in its record's `expect-results` with its own meaning (the proposed shared `2` = precondition-failed was declined at the gate — the registry's de-facto 1/2 use is per-case, `mts-access-after-reclaim-heap` declares two flavours of *staging* failure, and merging them would erase the condition information the Issue-1 decision requires keeping). **What `1` means, exactly (the ND-vs-PF criterion, stated so the rule and the edit list cannot be read two ways).** `1` = **silence**: the attack was launched, the run ended with the attack's intended effect absent, and **the platform delivered no signal** — no caught fault, no signal death, no execution of the attacker's target. It is the contrast class to the signed outcomes: a *responded* attack is 15–31 (a caught exception) or 256+signo (an uncaught one), and a *succeeded* one is 0. Inside `1` sit two realities the exit code deliberately does not separate — a **silent** defense neutralized the attack (the allocator cleaned the freed bytes; ASLR randomized the addresses; the RA write did not take under a calibrated offset) or the attack's mechanism never landed (a mis-targeted write, a compiler-optimized-away store) — because the bench's own stance (`INTERNAL.md`, "Interpret Test Results") is that the defender's identity (compiler, runtime, kernel, hardware) and even its existence cannot be read off the exit code; the argument sweeps and the calibration `require` chains do that work. Where a case *can* tell the two apart, the distinction is carried as a case-local value, as the mts reclaim pair already does (`1` = the freed space was refilled or cleaned = a silent defense acted; `2` = failed to reallocate a block = the attack never got staged). *Precondition failed* = the case could not stage or measure the attack at all — a required allocation, measurement or input was absent (e.g. "failed to get a reallocated block", "the frame size was not measured", "the side file holds no usable opcode word", "RA not found"). Only that PF class moves off the shared `1`. Two carve-outs: the scheduler itself renders a **65** temp-file failure as `2` (`scheduler/run-test.cpp:773-776`), so a `2` in a `set-var` record's results may be scheduler-generated rather than a case delivery; and a **staging/calibration producer's failure constant stays undeclared by design** (Step 5 — declaring it would satisfy a dependent's `require` gate and run the dependent on a failed input). **15–31** = the caught-exception/library band: `RT_CODE_MAPERR` = 15, `RT_CODE_ACCERR` = 16, 17/18 in use by `cfi/call-wrong-vtable-released`, `RT_CODE_MISMATCH` = **19** (the fixed handler's unmatched-fault delivery — a diagnostic, declared only if the census proves a designed scenario reaches it), `RT_CODE_LIBFAIL` = **20** (the library's own install/reset/pool guards — a configuration failure, never a designed outcome, declared nowhere), `RT_CODE_FAULT_CONTAINED` = **21** (the fakefunc corruption's contained fault); the MTESERR **9** enters as a named *match predicate* (`RT_SICODE_MTESERR`), never a status. **32–63** = runtime-parameter delivery (`32 + value`, the value asserted in `0..31` at the producer — **fifth-audit carve-out: the two same-call-site carriers deliver their *measured* frame offset as-is, because a bound there makes their declared exception `251` undeliverable and hands the ASan lane an undeclared `2`; the bound is applied only where the case has no declared out-of-band value (`acc/get-ra-offset.cpp`)** — consumed by `set-var` into `variables.json`); **64–65** = the temp-file variant — contract-mandated, retained, never a verdict. **1024/1025** scheduler-owned; **256+signo** signal deaths; **255 is not a code** — only the POSIX rendering of a negative/out-of-range status, and it may never be declared in `expect-results`; this is why every shipped `-1` is replaced (Issue-3). `gvar` stays control-flow state: it may gate branches and carry a calibration datum into the parameter channel, but it never becomes a verdict code. **The caught-exception registrations must keep the entry-vs-inside discrimination** (third audit, High — it reverses a gate-confirmed finding): a fault **at the target address** means the platform *denied* execution (defense → 16), while a fault **past the entry** (`m+4`) *proves the injected code began executing* (attack succeeded → **0**, the designed delivery, documented at INTERNAL.md:349 and introduced by `8979ee0`). `0` therefore enters the vocabulary as the **named** `RT_CODE_SUCCESS = 0`, the literal `0`s in the `m+4`/`addr+4` SIGILL/SIGFPE registrations become that name, and the `(e)` zero-form forbids only *negative* `rv_code`s and *unnamed* zeros — never the success constant. `41152e9` (the commit that broke the guard) silently substituted `RT_CODE_ACCERR` for the designed `0` on `cfi/code-injection.cpp`'s executed-path registrations; this cycle restores it.
**Constants live in a new `lib/include/result.hpp`, which owns the whole `RT_CODE_*` family** (both platform headers include it and drop their own definitions), and its "no constant outside 0–31" rule is scoped to *status* constants. Two out-of-band values are named **exceptions**, documented rather than smoothed away: `code-injection`'s **99** (hwasan's tag-mismatch *process* value, verified on this toolchain 2026-10-22 — the registration's `rv_code`, paired with the MTESERR `si_code` *predicate* 9) and **251** (the shipped ASan frame-shape value on the two same-call-site records; 251 = 32+219 is a *measured* offset, not a staging failure, so the two carriers keep delivering it and the round-4 producer bound is **removed** there — fifth audit, its single High: the bound made 251 undeliverable and delivered an undeclared `2` on exactly the ASan lane the exception documents; the range stays a documentation of designed values, enforced at the producer only where the record declares no exception). **R1 amends the published contract** — the caught-exception band's lower bound moves 16 → 15, and 19/20/21/99 are minted; Step 7 rewrites both published tables and the `CLAUDE.md` bullet, and the `## Document Overrides` row is the amendment's record.

**Declarations (gate ruling 2026-10-22; the third audit's measurement, then the user's 2026-10-22 ruling, settle the `.rodata` question).** `16` is declared on **all four** dp2fp records as the *denial* outcome — the platform refused to execute the injected code — and that is all: **the code is declared like any other expected result, with no `.rodata` narrative and no `comment` rationale** (user ruling: "as we now add 16 to the expected result, no need to record anything"). The measurement behind it stands as census input, not as documentation: on the reference lane `.rodata` sits in a **non-executable LOAD segment** (`readelf -lW`, segment 04), so the `-rodata` variant's illegal call faults `SEGV_ACCERR` at the entry and the fixed handler delivers 16 — while a platform that *executes* the injected code delivers `0` = attack succeeded. Only `99` on the `cfi-code-injection`-backed records stays a genuinely proactive declaration: MTE tag-checks data accesses, not instruction fetches, so no current lane reaches the tag-fault path — and the two numbers stay distinct, since the registration's *predicate* is the MTESERR `si_code` (9) while its *delivery* is `rv_code` 99; the 99 observed on this toolchain 2026-10-22 is HWASan's own runtime exit, which bypasses the case's handler entirely (the env lane's MTE CPU pin is rejected by this host's qemu, so the software-check path is what ran). The census is what keeps a proactive declaration honest: it asserts the *delivery* per case and storage class, and a pinned proactive code it cannot provoke is an admissible **"kept, unprovokable on the current lanes"** outcome — never a mismatch.

**Problem.** Three linked defects share one root: the process status is not treated as a contract. (1) ~20+ CFI cases (plus `cpi/modify-GOT.cpp` and others the enumeration will pin) deliver `gvar()` — a control-flow state variable — as `return gvar()` / `exit(gvar())`, including deliberate negative sentinels (`gvar_init(-2)`), decrement underflow, data-derived values (`strtol` over a non-NUL-terminated char, `(unsigned int)` of a double, argv digits), and `gvar()±k` arithmetic; POSIX renders `exit(-1)` as 255, so the registry sees codes the contract does not define. (2) Fifteen CHERI/Morello handoff lane-rows over fourteen records (codes 1/2/3/4/255) sit undeclared because the sweep could find no containment evidence — several of these codes are in fact the cases' designed failure paths, expressed through the same fragile delivery. (3) `cfi-return-to-parent-wrong-call-site-fakefunc` exits its designed `-1` (→255) and alternates with 267 natively (the record's 16 `-size` variants), and `cfi-jump-func-ra-from-heap-memcpy-implicit-arith` faults (267, SIGSEGV) on both riscv64 venues while scoring 0 on x86_64/aarch64 — its riscv64 path is an unmanaged crash, not a designed outcome. (4) The POSIX caught-exception handler does not honour its own matching: the `exit` sits outside the `if` (a 2023 regression — `41152e9` inserted `psignal` into a brace-less `if`, and `30bb0c6` later braced only the print), so the delivered value is whichever registration was pushed last, the signo/si_code/address predicates and the mismatch path are dead, and — because the newest registration in each dp2fp/code-injection case is the `m+4`/`addr+4` executed-path pair — a fault the platform raised to **deny** execution is reported with the executed path's value instead: for the four dp2fp cases that means **0 = attack succeeded**, i.e. the defense is read as a successful attack. (The `rv_code 0` itself is *designed* — it is the executed path's success delivery, INTERNAL.md:349; only the broken guard put it on the denial path. The third audit corrected this plan's earlier "polarity inversion" reading, and the same commit `41152e9` silently substituted `RT_CODE_ACCERR` for the designed `0` on `cfi/code-injection.cpp`'s executed-path registrations, collapsing the executed-vs-denied discrimination there.) The Windows sibling handler already has the intended structure; POSIX is brought to parity.

**Approach.** The registry's `expect-results` maps codes to meanings (precedent: `1` = "failed to change RA on stack at all", `251`/`267` toolchain-quirk meanings, SIGPROT `290`) — so every surviving code gets a named constant and a declared meaning, and nothing is declared without containment evidence (the sweep's (D)-discipline). The delivery is made deterministic: one status, one constant, no arithmetic, no data path — with the parameter channel carved out as the one contract-mandated exception. The two problem cases get their failure paths fixed (the fakefunc case delivers its designed constant and contains its fault path through the portable caught-exception mechanism; the riscv64 case's path is investigated from the recorded SIGSEGV signature — `scause 13`, faulting `lw a5,8(s0)` with `s0=2`, i.e. the case state read as a pointer — and, if that shows a lib/riscv64 port fault rather than a contained attack, is deferred rather than patched from inside a case).

**Rollback.** The change lands as one bench commit, so backing it out is a revert plus the env successor's pin bump. Forward-only is accepted: a mis-declaration discovered after the pin bump is corrected by a follow-up commit + pin bump, never by in-place stamp surgery.

**Out of scope:** the env successor's lane re-runs (pin bump; the F2/267 row's lane closure there) — for its checklist: this host's `qemu-aarch64` 10.2.1 rejects the lane's own `QEMU_CPU=max,mte=on` pin (`Property 'max-arm-cpu.mte' not found`) while `results/aarch64-mte/*/results.dat` asserts `# CPU: max,mte=on`, so the MTE lane's CPU-model claim should be re-verified before its next re-run; fixing the two platform defects (their own deferrals — Step 1 delivers the records, not the fixes); `INTERNAL.md`'s prose drift (outside the planner's allowlist — Step 7 files its deferral with the exact passage locations); the extraction/prologue observations in the env tracker.
