Porting

Test cases are written to be portable, so supporting a new instruction set or operating system means adding to the support library rather than touching the cases. This page describes the library layout, how a platform is selected at build time, and what a new port has to supply.

Support library layout

Directory Role
lib/include/ Portable headers that test cases include. assembly.hpp is the dispatch point: it inspects the compiler's predefined macros and includes the right per-ISA header. Also conf.hpp (buffer and region configuration), mss.hpp, cfi.hpp, signal.hpp, global_var.hpp, builtin.hpp, temp_file.hpp, and result.hpp — the RT_CODE_* family, the result-code vocabulary every port shares. A port's platform signal.hpp includes it and defines no constant of its own.
lib/common/ Portable implementations shared by every platform: global_var.cpp, temp_file.cpp, mss.cpp, and cfi.cpp (built into libcfi, linked by the cpi and cfi cases).
lib/x86_64/ x86-64 support: assembly.hpp, assembly.cpp, indepassembly.asm, plus visualcpp_assembly.hpp and visualcpp_indepassembly_func.asm for MSVC.
lib/aarch64/ AArch64 support (also used for Morello builds under enable_aarch64_morello). Morello assembles the variant indepassembly_morello.asm in place of indepassembly.asm, because the plain AArch64 bodies are rejected under -mabi=purecap.
lib/riscv64/ RISC-V 64 support.
lib/cheri_riscv64/ CHERI RISC-V support, selected by enable_riscv64_cheri, which also forces ARCH to this value.
lib/posix/ The POSIX/ELF OS layer: signal handling (signal.cpp, signal.hpp) and gcc_builtin.hpp.
lib/visualcpp/ The Windows MSVC OS layer: signal.cpp, signal.hpp, msvc_builtin.hpp.

How a platform is selected

Two independent axes are chosen at build time. ARCH selects the instruction set and therefore lib/<arch>/; CLIBAPI selects the OS/ABI layer and therefore lib/<clibapi>/. Test cases include only portable headers and never reference either directly. 

lib/include/assembly.hpp      the ISA dispatch point
lib/include/result.hpp        the RT_CODE_* result-code vocabulary, shared by every port
  #if defined(__x86_64) || defined(_M_X64)   -> CSB_X86_64, lib/x86_64/assembly.hpp
  #if defined(__aarch64__)                   -> lib/aarch64/assembly.hpp
  #if defined(__riscv)                       -> lib/riscv64/assembly.hpp

Makefile
  ARCH    ?= x86_64                    (on Windows)
  ARCH    ?= $(shell arch)             (elsewhere; arm64 is mapped to aarch64)
  CLIBAPI := visualcpp | posix         (chosen from the detected platform)

The Makefile's ARCH values are x86_64 (the default), aarch64 (from an arm64 host, or forced by enable_aarch64_morello), riscv64 (from a riscv64 host), and cheri_riscv64 (forced by enable_riscv64_cheri).

Hardware feature switches in the same style as the generic security flags add the required architecture options, for example -march=armv8.5-a+memtag for enable_aarch64_mte, -march=armv8.3-a+pauth for enable_aarch64_pa, -march=armv8.5-a -mbranch-protection=bti for enable_aarch64_bti, --target=aarch64-unknown-freebsd -march=morello -mabi=purecap for enable_aarch64_morello, and --target=riscv64-unknown-freebsd -march=rv64gcxcheri -mabi=l64pc128d for enable_riscv64_cheri.

These switches configure flags only; they do not select a compiler. The default toolchain (g++ / as) rejects the Morello and CHERI options, so a build using them must also be pointed at toolchains that understand them — pass CXX= and ASM= on the make line, as every non-host lane does. Both CHERI switch blocks carry their --target triple themselves (the Morello clang and the CTSRD clang otherwise default to the host triple and reject -mabi= outright), so a purecap build additionally needs the compiler's purecap sysroot, passed through CXX= (for example --sysroot=<sdk>/sysroot-riscv64-purecap); the riscv64 CHERI build also passes ARCH=cheri_riscv64 on the make line, because the independent-assembly object is selected from ARCH before the switch forces it.

What a test case links against

Every case links the portable objects, the architecture's assembly object, the OS layer's signal object, and the architecture's independent-assembly object: 

lib/common/global_var.o  lib/common/temp_file.o
lib/<ARCH>/assembly.o    lib/<CLIBAPI>/signal.o    lib/<ARCH>/indepassembly.o

On top of that, the mss and mts categories also link lib/common/mss.o, and the cpi and cfi categories link libcfi (built from lib/common/cfi.cpp) — which is why those categories test pointer and control-flow integrity through a separate helper rather than inline. The indepassembly object is assembled from lib/<ARCH>/indepassembly.asm, with the MSVC variant lib/x86_64/visualcpp_indepassembly_func.asm used on Windows. Under enable_aarch64_morello the Morello variant lib/aarch64/indepassembly_morello.asm is selected instead, so the link line above carries indepassembly_morello.o for that configuration.

A port whose indepassembly.asm is not translated yet can omit the object with the disable_independent_assembly build switch. There are three routes, and the second is the one a scheduler-driven run needs — the scheduler launches its own make for each case, and a variable assignment in MAKEFLAGS reaches those child makes with command-line strength: 

make disable_independent_assembly=yes
MAKEFLAGS='disable_independent_assembly=yes' ./run-test exhausted-run

The third route is the flag menu's #disable_independent_assembly = yes line, uncommented like any other flag (see Architecture). With the object omitted, the two programs that call its symbols — cfi-return-to-peer-asmfunc and cfi-return-to-parent-non-call-site-by-asmfunc — fail to link: the scheduler records them as 1025 (not run) and the rest of the suite builds and runs normally. The switch is a bring-up interim, not a supported final configuration: once the port is otherwise complete, give those two records a skip list naming the architecture instead, so the gap is declared rather than left to fail the build.

Adding an instruction set

  1. Create lib/<arch>/ containing assembly.hpp, assembly.cpp and indepassembly.asm. The headers define the macro bodies the test cases call — the ones that modify a return address, read a code page, relocate a pointer — as embedded assembly, and the .cpp holds whatever the inline forms cannot express. The port can come up before the .asm is complete: build with disable_independent_assembly and the rest of the suite measures the new ISA while that assembly is translated (see “What a test case links against” above).
  2. Add the dispatch branch to lib/include/assembly.hpp, keyed on the macros the target compiler predefines, so the new header is selected on that ISA.
  3. Check the Makefile's ARCH detection maps the host to the new value. Where the port is selected by a hardware feature rather than by the host alone, follow the enable_riscv64_cheri and enable_aarch64_morello pattern, which set ARCH from the flag.
  4. Provide an opcode-extraction script if the generated acc-read-func.gen case is to work, named script/get_<arch>_func_inst.sh and wired through the Makefile's func-opcode-gen. It extracts, from the built binary, the eight code bytes that case compares against, disassembling with the platform's OBJDUMP (below), and it fails loudly when that tool cannot decode the binary rather than emitting a wrong word. Existing examples are the x64, aarch64, riscv64 and cheri_riscv64 scripts — the last requires a CHERI-capable objdump (the CTSRD SDK's riscv64cheri-objdump, a wrapper over llvm-objdump), because a plain riscv64 objdump decodes xcheri binaries only partially and exits non-zero.
  5. Run the suite with ./run-test exhausted-run so every case is attempted regardless of prerequisites, and compare the result distribution against an existing port to find cases whose embedded assembly was not correctly translated.

Adding an operating system

  1. Create lib/<clibapi>/ supplying signal.hpp, signal.cpp and a builtin header, following lib/posix/ or lib/visualcpp/. The signal layer is what lets a case catch an expected fault and report it as a defined result code instead of an unexplained crash. The port's signal.hpp includes lib/include/result.hpp for the RT_CODE_* constants and defines no result-code constant of its own: the vocabulary has exactly one home, so a port cannot drift from it.
  2. Set CLIBAPI for the platform in the Makefile, and make sure the toolchain selection (CXX, ASM, OBJDUMP, the object and executable naming, the linker flags) matches it. OBJDUMP must disassemble the binaries this platform produces: besides the dump target and sys_info.txt, it drives the opcode extraction described above, so a tool that cannot decode those binaries fails the corpus build instead of quietly producing a wrong extraction.
  3. Confirm the ISA dispatch still applies, since lib/include/assembly.hpp resolves the OS layer for some ISAs — on x86-64 the MSVC build selects visualcpp_assembly.hpp instead of the generic header.

The named result codes a port must produce are owned by lib/include/result.hpp and documented in Architecture; a new platform is correctly ported when its cases return those codes with the same meanings and its platform signal.hpp adds no constant of its own.
