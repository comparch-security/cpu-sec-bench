Architecture

The benchmark is deliberately split in two: a set of portable test cases, and a shared support library that holds everything platform-specific. This page describes how a test case is written, how the scheduler turns the configuration registry into a sequence of builds and runs, and how a run's exit status is interpreted.

Two-part design

Every test case is a short C++ program that creates one vulnerable situation at run time and reports whether the attack succeeded. Most of the code is portable, but an attack that a compiler can see through would be optimized away, so where that risk exists the case calls a macro whose body is embedded assembly. Those macro bodies are the platform-specific part of the suite and live in the support library, never in the test case. 

lib/include/assembly.hpp      selects the implementation by ISA
  __x86_64 / _M_X64  ->  lib/x86_64/assembly.hpp   (or visualcpp_assembly.hpp under MSVC)
  __aarch64__        ->  lib/aarch64/assembly.hpp
  __riscv           ->  lib/riscv64/assembly.hpp
lib/include/result.hpp        owns the result-code vocabulary (the RT_CODE_* family)
lib/posix/ or lib/visualcpp/  the OS/ABI layer, chosen by CLIBAPI

A test case therefore contains no assembly, no signal handling and no ABI knowledge: it calls something like MOD_STACK_DAT(label, offset) and the library decides what that means on this platform. See Porting for the full layout and for what a new port must supply.

The scheduler

scheduler/run-test.cpp is the only thing the default Makefile target builds. It compiles test cases on demand, runs them, and records what happened.

  1. Read the registry. configure.json is parsed into the configuration database. With continue, results.json is read first so already-recorded cases can be skipped, and variables.json is loaded into the variable database that -v arguments read from. A malformed or truncated JSON file exits 1 with a message instead of aborting.
  2. Compute the pending list. Every record not yet present in the results database is a candidate. A record whose skip list names the architecture the scheduler was built for is recorded as 1025 — not run — and never built or run. This check precedes argument expansion and prerequisite gating, so a skipped record is recorded even under make-only and is never requeued by an unsatisfied prerequisite.
  3. Expand the arguments. A record's arguments (or default_args under exhausted-run) list is expanded. An entry beginning with -r, -l or -v names a property rather than being passed literally: -r takes a range, so "arguments": ["-roffset"] with "offset": [0, 8, 1] launches the program eight times, once per value; -l takes a value list; -v substitutes a runtime variable discovered earlier in the run.
  4. Gate on prerequisites. The require property is a list of lists. Each inner list is a disjunction — any one of its cases passing satisfies it — and the outer list is a conjunction of those groups. A case whose prerequisite group is unsatisfied is recorded as 1024 and not run. A prerequisite counts as passing when it exited 0 or with a code the prerequisite's own expect-results declares as acceptable.
  5. Build on demand. The case is built as make -B test/<program> MACRO=value …, with the macro assignments taken from the record's conf-macro map. The scheduler rebuilds only when that map differs from the last successful build, so several records that share a macro set share one binary. A build that fails is recorded as 1025 as well — the case was not run — with make's own exit status kept in the record's make-status field and printed in the log, so a raw build status is never mistaken for a test outcome. In corpus mode the -B branch is always taken and each fresh build is snapshotted — see Corpus mode below.
  6. Run and interpret. test/<program> is spawned with the expanded arguments and its exit status classified as below. A status in the runtime-parameter range is consumed rather than recorded as an outcome. In corpus mode the spawned path is the snapshot test/<program>__<key>, and a missing snapshot ends the run rather than the case.
  7. Record. The outcome is written into results.json, which is rewritten after every case, so an interrupted run leaves usable partial state. With a reporting option, results.dat is then written, prefixed by the contents of test/sys_info.txt (CPU, system, compiler versions and the flags that were in force) — or by a placeholder line when that file is missing or unreadable, and with a bounded copy loop that also terminates on a line longer than its buffer or a mid-read failure. Two summary lines then count the records that were not run: # not run (skipped for this platform): N and # not run (failed to build): M. A platform that cannot run or build part of the suite therefore shows the gap explicitly rather than losing that coverage silently.

Corpus mode: build elsewhere, run here

A venue may have no compiler. The motivating case is a booted guest under an instruction-set simulator: it carries the benchmark's binaries and its scheduler, but nothing that could build them. The corpus option splits the two phases across machines — the suite is compiled on a build host, one binary per (program, macro-map) build unit, and that set is what the run host executes. 

# build host: build and snapshot every unit
./run-test corpus make-only exhausted-run
# run host: execute the snapshots, never build
./run-test no-make corpus exhausted-run

In the build phase corpus forces the -B branch even for an empty macro map, so every unit is rebuilt, and after each successful build it copies test/<program> to test/<program>__<key> — the file the run phase will execute. <key> is a deterministic 8-hex-digit FNV-1a-32 (offset basis 0x811c9dc5, prime 0x01000193) over the record's macro map rendered as KEY=VALUE pairs with the keys sorted and the pairs comma-joined. The map is ordered, so that string is canonical and the key depends on nothing else — not on build order, not on a counter — which is what lets a name identify its build unit on any machine. An empty macro map therefore keys to 811c9dc5, the hash of the empty string.

That rendering assumes no macro value contains a , followed by KEY=. A value that did — and macro values may legitimately contain commas — would render exactly like a map with one more pair, so two different build units of one program would share a key and the later snapshot would silently replace the earlier one. No value in the shipped registry comes close, and the manifest script's per-program collision check would catch a hash collision but not this aliasing; the assumption is part of the contract, so a record that needed such a value would have to have the rendering escaped first.

In the run phase corpus replaces test/<program> in the run command with the keyed path, and a missing corpus file is fatal: the scheduler writes corpus file missing: <path> to stderr and exits 1 instead of recording a result for a case that never ran. Nothing else changes, so a corpus run records the same result values a normal run of the same records would; the record shape differs only in the fields a build writes (make-time, file-size), which a no-make corpus run has no occasion to set. Without corpus, both phases behave as they always have.

The snapshot is also what keeps variant records honest across the split. The in-place test/<program> is overwritten whenever the macro map changes, and many programs in the shipped registry carry several variants (the catalogue page lists them, and script/check_catalog.py derives the current totals), so a plain make-only followed by no-make would run whichever variant happened to be built last. The supported split is run-test corpus make-only at build time and run-test no-make corpus at run time.

Result codes

Exit status is the interface between a test case and the scheduler, so the contract is fixed and each range has exactly one meaning. The named 0-31 values and their constants are owned by lib/include/result.hpp and documented here; the scheduler encodes the parameter channel (32-63), the temp-file variant (64-65), signal deaths (256+signo) and its own 1024/1025, and adds nothing to the 0-31 families. The same contract is summarised for users in README.md.

Code Meaning
0 The test passed — the vulnerability was successfully exploited, so the platform does not provide the corresponding defense.
1 The attack was launched, no platform signal was delivered, and the attack's intended effect is absent — silence. It is the single shared not-demonstrated constant, and it deliberately does not separate two realities: a silent defense neutralized the attack, or the attack's mechanism never landed. The argument sweeps, the require chains and the case-local values (where a case can tell them apart) carry that distinction, which no exit code can. The mss redzone family is the worked example: the out-of-bounds access simply did not land in the target buffer. It is never to be read as “the platform stopped the attack”.
2-14 A case-local failure value: meaningful only for the case that delivers it, and declared in that record's expect-results with its meaning. There is no shared value in this range.
15-31 The caught-exception and library band: the platform responded to the attack. An expected exception was caught and a defined constant returned — this is how a defense that manifests as an exception (DEP, for example) is recorded as an expected outcome rather than an anomaly. The named values are 15 (RT_CODE_MAPERR) and 16 (RT_CODE_ACCERR) for the caught memory faults, 17 and 18 (in use by cfi-call-wrong-vtable-released), 19 (RT_CODE_MISMATCH, the handler's unmatched-fault diagnostic, declared only when a designed scenario reaches it — on a PAuth build a forged return address rejected by authentication raises SIGILL/ILL_ILLOPC, which matches no registration), 20 (RT_CODE_LIBFAIL, a library configuration failure) and 21 (RT_CODE_FAULT_CONTAINED, the fakefunc corruption's contained fault). The constants live in lib/include/result.hpp.
32-63 A runtime parameter was discovered: the value is the code minus 32. The scheduler stores it in variables.json and treats the case as successful, so later cases can consume the value through a -v argument. The producer bounds the value to 0..31 wherever the case declares no out-of-band value; that bound is not enforced at the consumer, and 251 (32 + 219, the ASan frame offset) is the shipped demonstration of a designed out-of-band delivery.
64-65 The same discovery, but the parameter was written to a temp file instead of encoded in the status. 64 is then treated as success and 65 as code 2.
256-511 The process was terminated by a signal; the signal number is the code minus 256. This is what the scheduler records for a crash the test case did not catch.
1024 A prerequisite case failed, so this case was not run.
1025 The case was not run: it is skipped on this platform (the record's skip list names the architecture the scheduler was built for), or it could not be built. For a build failure, make's raw exit status is kept in the record's make-status field rather than shown as the result. This code is scheduler-owned and never a test case's own outcome.
other Something is wrong and needs investigation.

The scheduler prints and highlights only unexpected codes, so a clean run is quiet and anything needing attention stands out. Negative and out-of-range process statuses are never codes: POSIX renders them as 255, so 255 appears in this suite only as that rendering — it is never declared in a record's expect-results, and a case that reaches it has a defect to fix rather than a result to record. Three rules complete the contract. gvar is control-flow state: it may gate branches and carry a calibration datum into the parameter channel, but it never becomes a verdict code. A caught fault at the target address means the platform denied execution (a defense), while a fault past the entry proves the injected code began executing — the attack succeeded, and 0 is the honest delivery. And 99 is declared per record for the MTE/HWASan build class: the aarch64-mte lane's HWASan runtime delivers it when the tag check catches the access (MTE tag-checks data accesses rather than instruction fetches), and the record's meaning string names that class. The same two values are named exceptions outside the bands, documented in lib/include/result.hpp: 99 and the registry-side 251.

Runtime parameters

Some values cannot be known at build time. The canonical example is the offset of the return address from the stack pointer: it depends on the ABI, on whether a frame pointer is used, and on whether instrumentation such as a stack canary changed the frame. Every return-oriented test needs it.

The suite obtains it by measurement rather than assumption. A calibrating case is launched once per candidate offset in the range declared by its offset property; the run that manages to hijack the return address exits with 32 plus that offset, and the scheduler stores the value under the name the record gives in set-var. Those names are per-region rather than global: acc-get-ra-offset-v-p-g0 and -g1 calibrate stack-offset-v-p-g0 and stack-offset-v-p-g1, and cfi-return-to-parent-same-call-site calibrates the latter as well. A dependent record such as cfi-return-to-parent-wrong-call-site then receives it through a -vstack-offset-v-p-g1 argument, and the require graph guarantees its calibration case runs first.

A case may instead derive the slot at run time, without consuming the calibrated value, when its own frame's shape differs from the calibrating case's: it locates the saved return-address slot by the value the slot holds (cfi-return-to-peer-asmfunc does this), which keeps one frame's layout assumption out of another frame's. The calibrated names remain the general channel; such a case simply needs no -v argument for it.

Configuration registry

configure.json is the authoritative description of the suite: one record per testable configuration. Record keys are <category>-<name>, and a record is a program plus the macros and arguments that specialise it.

Field Purpose
program The source basename to build. When absent, the record key itself is the program name — which is why a record whose name is not its program's name must state this field.
conf-macro Compile-time macro assignments, keyed by argument-list index. A change here is what forces a rebuild.
arguments Runtime arguments, with -r / -l / -v expansion.
default_args Alternative argument list used by exhausted-run, for running every case without the prerequisite pruning that normally narrows the set.
require The prerequisite graph: list of lists, inner OR, outer AND.
require-comment Classifies each prerequisite edge as either utilization or relaxation — the only two tokens the suite uses — so the relation graph can be rendered by type.
skip Platforms the record is not runnable on: an array of ARCH values. When it names the architecture the scheduler was built for, the record is recorded as 1025 and neither built nor run. The shipped registry declares none — the field exists so a port in progress can state what it cannot run yet instead of leaving unexplained build failures.
skip-reason Free-text reason printed with the skip notice, so a skipped record explains itself in the run log.
expect-results Non-zero exit codes that are acceptable outcomes, each mapped to its meaning. A case exiting with one of these codes did not demonstrate the exploit — only exit 0 does — so the run is recorded with that code's meaning rather than flagged as an unexpected result.
set-var Names the runtime variable this case calibrates, so the scheduler stores a discovered parameter under it.
get-code-offset Names the function and target symbol whose code offset is extracted from the built binary by a script before running.
size Range for the allocation-size arguments a case sweeps.
offset Range for the stack-offset sweep used to calibrate return-address tests.
extend_offset Widens an offset sweep beyond the default range.
reference The source paper or technique a case is derived from.
comment Free-text note on the record's intent.
todo Known gaps or planned extensions for this record.
multitry Marks a case that is expected to be retried rather than judged on a single attempt.

Build configuration

Security features are selected by Make variables rather than by editing the Makefile, so a single checkout can be measured under many configurations. The available switches are listed as a commented menu near the top of the Makefile, and each is passed on the command line: 

make enable_stack_protection=yes
make disable_aslr_protection=yes enable_control_flow_protection=yes

The Makefile chooses ARCH from the host (arm64 is mapped to aarch64; enable_riscv64_cheri forces cheri_riscv64) and CLIBAPI from the platform (posix, or visualcpp under MSVC). Selected flags are recorded into test/sys_info.txt and therefore appear at the head of every results.dat, so a result file is self-describing.

Relations between cases

Cases are not independent. Two kinds of relation are recorded in require-comment, named by the same tokens configure.json uses:

  • utilization — A can only be exploited if B can be. An out-of-bounds read past an array inside an object utilizes the intra-object redzone check and the data-pointer-arithmetic check, which is why mss-read-by-enclosing-array-index-overflow-* records require acc-check-intra-obj-*-redzone and acc-check-data-pointer-arithmetic-*.
  • relaxation — A is the more evasive variant of B. Returning to a plausible call site is harder to detect than returning anywhere, so the latter is the relaxed form.

In every kind, if the prerequisite is defeated by a defence then the dependent case is almost certainly defeated too, so it does not need to be tested. That is what makes the run prunable: following the graph from the cases with no prerequisites gives the coverage actually reached, and script/gen_relationship.py renders the whole graph from this registry.
